## UI Flow Analysis

### 1. Assessment Scoring Tab ([AssessmentScoringTab.tsx](src/pages/AssessmentScoringTab.tsx))

**Current UI Behavior:**

```typescript
// Hierarchical Table Structure:
// - Cyber Risk (parent row) - shows aggregated scores
//   └─ Scenario 1 (child row) - individual scenario scores
//   └─ Scenario 2 (child row) - individual scenario scores
//   └─ Scenario 3 (child row) - individual scenario scores

type ScoringRow = {
  kind: "cyberRisk" | "scenario";
  impact: ScoreValue;              // 1-5 with label
  threat: ScoreValue;              // "Threat severity"
  vulnerability: ScoreValue;        // "Vulnerability severity"
  likelihood: ScoreValue;           // Calculated (T×V)
  cyberRiskScore: ScoreValue;      // Calculated (I×L)
}
```

**AI Scoring Flow:**
1. User clicks **"Start AI scoring"** button in `ScoringInfoCard`
2. UI shows skeleton loaders while `aiScoringPhase === "processing"`
3. Agent scores ALL scenarios in the assessment (batch operation)
4. Scores populate in the table (lines 316-319)
5. User can click any scenario row to view/edit rationale

**Key UI Properties:**
- **Column Headers** (lines 897-902):
  - "Impact" (not "Asset criticality")
  - "Threat severity" ✅ matches spec
  - "Vulnerability severity" ✅ matches spec
  - "Likelihood" (calculated)
  - "Cyber risk score" (calculated)

- **Aggregation Methods** (lines 751-769):
  - `"highest"`: Pick highest value among child scenarios for each metric
  - `"average"`: Arithmetic mean of I/T/V, then calculate L and CRS
  - Parent rows recalculate Likelihood and Cyber Risk Score from aggregated I/T/V

## Gap Analysis

### ❌ Gap 1: Missing "Impact" in Agent Output

**Current Spec:**
```typescript
interface ScoringOutput {
  threatSeverity: 1-5;
  vulnerabilitySeverity: 1-5;
  // ❌ Impact is NOT in output (assumes asset.criticality)
}
```

**UI Expectation:**
```typescript
// From AssessmentScoringTab.tsx:316
impact: toFivePointScore(s.impact, s.impactLabel)
```

**Issue**: The agent spec assumes Impact = Asset Criticality automatically, but the UI shows "Impact" as a separate column that CAN be overridden by users (lines 199-220 in ScenarioScoringDropdownsBlock).

**Fix Required**: 
✅ **Keep spec as-is** - Impact DOES equal Asset Criticality for inherent scoring. Users can override it manually in the UI, but the agent doesn't need to score it.

### ⚠️ Gap 2: Batch vs. Individual Scoring

**Current Spec:**
- Designed for **single scenario** scoring
- Section 10.2 mentions batch processing but lacks detail

**UI Reality:**
- **"Start AI scoring"** processes **ALL scenarios** in assessment (lines 598-600)
- Shows skeleton loaders for entire table
- No way to score individual scenarios via UI button

**Fix Required**:
Add to specification:

```markdown
### 10.2 Batch Processing Requirements

When the user triggers "Start AI scoring" from the Assessment Scoring Tab:

1. **Input**: Array of all scenarios in the assessment scope
2. **Processing**: Score each scenario independently (no cross-scenario context)
3. **Progress**: Optionally report progress (X of Y scenarios completed)
4. **Atomicity**: ALL scenarios must complete before updating UI
5. **Error Handling**: 
   - If ANY scenario fails, preserve successful scores
   - Flag failed scenarios for manual review
   - Return partial results with error list

**Batch Output:**
```typescript
interface BatchScoringOutput {
  results: ScoringOutput[];
  summary: {
    total: number;
    succeeded: number;
    failed: number;
    flaggedForReview: number;
  };
  errors?: Array<{
    scenarioId: string;
    error: string;
  }>;
}
```
```

### ⚠️ Gap 3: Rationale Format Mismatch

**Current Spec Example** (very detailed, ~400 words):
```markdown
**Threat Severity: 4 - High**

**Scoring Basis: Inherent Risk (without controls)**

**Key Factors Analyzed:**
1. **Threat Actor Capability**
   - Primary Actor: Organised Cybercriminal Group
   ...
```

**UI Display** ([ScoringRationalePage.tsx:510-518](src/pages/ScoringRationalePage.tsx#L510-L518)):
- WYSIWYG rich-text editor
- Supports markdown rendering
- User can edit freely
- History panel shows full rationale (collapsible)

**Issue**: The structured format is EXCELLENT for history/audit trails, but:
- ✅ **Pros**: Detailed, consistent, auditable
- ⚠️ **Cons**: VERY verbose (400+ words per scenario)
- If an assessment has 50 scenarios, that's **20,000+ words** of AI-generated text

**Recommendation**:

1. **Keep the detailed format** for the agent's internal reasoning
2. **Generate TWO rationales**:
   - **Full Rationale** (current spec format) - stored in database for audit
   - **Summary Rationale** (150-250 words) - displayed in UI by default

```typescript
interface ScoringOutput {
  // ... existing fields ...
  
  threatRationale: string;           // Full detailed format
  threatRationaleSummary: string;    // Concise 2-3 paragraph summary
  
  vulnerabilityRationale: string;
  vulnerabilityRationaleSummary: string;
  
  // Combined scenario rationale
  scenarioRationaleForUI: string;    // What appears in the WYSIWYG editor
}
```

**Example Summary Format**:
```markdown
**Threat Severity: 4 - High**

This SQL Injection attack represents a high-severity threat due to organized cybercriminal actors targeting the payment processing server (criticality 5/5) via highly accessible web application vectors. The threat domain (Application & API) strongly aligns with the server asset type, and deliberate attack sources indicate intentional exploitation patterns.

**Vulnerability Severity: 4 - High**

The application security defect is highly severe given easy exploitability through well-known SQL injection techniques, dual CIA impact (confidentiality + integrity), and the critical nature of the payment server. Strong domain-asset alignment and documented exploitation methods make this vulnerability particularly concerning for financial data protection.

**Likelihood: 16 - High | Cyber Risk Score: 80 - High**
```

### ⚠️ Gap 4: Missing "Scenario Not Applicable" Handling

**UI Feature** ([AssessmentScoringTab.tsx:297](src/pages/AssessmentScoringTab.tsx#L297)):
```typescript
const na = scenarioNotApplicableIds.has(s.id);
return {
  // ...

**What This Means**:
- Users can mark scenarios as "Not Applicable" to this assessment
- N/A scenarios show in the table with "-" for all score columns
- Agent should **skip** scoring N/A scenarios

**Fix Required**:

```typescript
interface ScoringInput {
  // ... existing fields ...
  
  isNotApplicable?: boolean;  // If true, skip scoring this scenario
}
```

And Section 4.1:

```typescript
interface ScoringOutput {
  // ... existing fields ...
  
  skipped?: boolean;          // True if scenario was marked N/A
  skipReason?: string;        // "Scenario marked as Not Applicable to this assessment"
}
```

### ⚠️ Gap 6: Agent Context Awareness

**Current Spec**: Each scenario scored independently (Section 10.2: "Do NOT carry over context")

**UI Reality**: Scenarios are grouped by Cyber Risk

**Question**: Should the agent know about sibling scenarios?

**Example**:
```
Cyber Risk: "SQL Injection threat"
  ├─ Scenario 1: SQL Injection on Payment Server
  ├─ Scenario 2: SQL Injection on Customer Database
  └─ Scenario 3: SQL Injection on Test API
```

**Current Approach**: ✅ **Keep independent scoring**
- Maintains consistency
- Avoids context pollution
- Simplifies agent logic
- Users can review and adjust if needed

**Alternative** (NOT recommended): 
- Agent scores scenarios in groups
- Can create relative scores within cyber risk
- More complex, risk of inconsistency

**Decision**: ✅ Stick with independent scoring per spec
